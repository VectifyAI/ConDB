\title{\textbf{Storage Layouts for PageIndex Subtree Retrieval}}
\author{Junyao Dong}
\date{}

\begin{abstract}
PageIndex subtree retrieval reads Structure and Metadata but not leaf Text.
This report asks whether Structure and Metadata should be colocated and, after
selecting the faster layout, why MongoDB remains slower than PostgreSQL. We
evaluate two layouts on the same ten-million-node tree and 200 paths in
MongoDB, PostgreSQL, and SQLite. Colocation lowers P50 and P95 latency in all
three engines. In an interleaved causal run, mean latency is 77.8\,ms in
MongoDB and 59.7\,ms in PostgreSQL. Matched zero-fetch, ID-only, cursor-batch,
and scalar-count interventions show that the gap persists without document
access, returned rows, or an extra \code{getMore}. Direct count and key-shape
controls locate the difference in per-key index processing. PostgreSQL performs
the analogous B-tree, index-only-scan, and aggregate steps; it does not skip
them. Profiling the scalar control locates MongoDB's excess CPU in per-key
WiredTiger cursor/key extraction plus classic \code{COUNT\_SCAN} bookkeeping.
Client record processing adds a separate 5.3\,ms penalty.
\end{abstract}

\section{Introduction}

PageIndex stores three kinds of information: tree Structure, descriptive
Metadata, and leaf Text. A subtree request needs Structure to identify and
order descendants and Metadata to return their titles and summaries. It does
not need Text. This access pattern creates a physical-design choice: colocate
Structure and Metadata for one range scan, or separate them and retrieve
Metadata after the Structure scan.

We answer two questions. First, which layout gives lower subtree latency across
MongoDB, PostgreSQL, and SQLite? Second, under the better layout, what causes
the remaining MongoDB--PostgreSQL latency gap? The first question is an
end-to-end layout comparison. The second requires causal interventions because
a broad ``database fetch'' timer mixes index execution, document access,
transfer, decoding, and record materialization.

The benchmark is deliberately narrower than the full storage API. Its range is
root-exclusive and unbounded in depth, whereas the current
\code{get\_subtree} API includes the root and applies a depth limit. The results
therefore characterize descendant range retrieval, not complete API latency.

\section{Layouts and query paths}\label{sec:layouts}

Both layouts keep leaf text out of the subtree scan. They differ only in
whether the fields returned by \code{get\_subtree} are kept with the tree
structure. MongoDB implements each physical group as a collection. PostgreSQL
and SQLite implement each group as a table. Text remains separate in both
layouts and is read only when content is requested.

\begin{figure}[H]

\caption{The two layouts used for \code{get\_subtree}. Left: Structure and

The colocated layout needs one ordered range scan. The separated layout first
scans Structure for node IDs, fetches Metadata in batches, and restores the
original Structure order. Thus both layouts return the same logical rows, but
the separated layout adds database requests and client reassembly.

\section{Experimental methodology}\label{sec:method}

\subsection{Workload and environment}

The benchmark uses a ten-million-node tree and the same deterministic 200
subtree paths in MongoDB, PostgreSQL, and SQLite. The mean result size is
36{,}456.7 records per path. Both layouts are loaded side by side in each
engine. The text store is identical and is not read by this operation. The two
queries return the same ordered \code{(node\_id,title,summary)} list for every
path.

All runs use one client on the same dual-socket Intel Xeon Gold 6418H Linux host
with 48 physical cores, 96 hardware threads, and 1\,TiB RAM. MongoDB~7.0.34 and
PostgreSQL~16.14 run as localhost Docker services. SQLite~3.37.2 runs in
process. Database and operating-system caches are not cleared. Reported values
therefore include the observed cache state. All latency values are rounded to
one decimal place in the paper.

\subsection{Layout-comparison protocol}

Layout timing includes full result consumption and driver decoding. For the
separated layout it also includes every Metadata batch and ordered reassembly;
each Metadata request contains at most 1{,}000 node IDs. Each layout first runs
on the same three paths without timing. Every path is then timed once per
layout, and the layout measured first alternates by path. Comparisons are made
within each engine; SQLite's in-process values are not used as server-to-server
measurements.

\subsection{Cross-engine and causal protocol}

After the layout comparison selects colocation, MongoDB and PostgreSQL run one
full untimed sweep followed by three timed sweeps. Paths, query arms, and engine
order are interleaved; the path order rotates between repetitions. Every pair
returns the same row count, logical values, and order. Repetitions are first
averaged within each path, after which all 200 path means receive equal weight.
Every arm accesses only the colocated Structure-and-Metadata collection or
table; neither engine accesses the Text store or its index.

The initial breakdown has two additive stages. \emph{Database fetch} includes
server execution, localhost transfer, driver decoding, and materialization of
returned records. \emph{Client processing} includes normalization and cleanup
of decoded objects. Because the first stage is composite, we then introduce
zero-fetch exact-output, ID-only, cursor-batch, and scalar-count interventions.
The two zero-fetch arms use 40 row-count-stratified paths and are accepted only
when MongoDB examines zero documents and PostgreSQL performs zero heap fetches.
The scalar-count experiment uses the direct MongoDB \code{count} command and all
200 paths over five repetitions, reducing each result to one scalar. MongoDB
retains its native \code{COUNT} over \code{COUNT\_SCAN}, while PostgreSQL retains
\code{Aggregate} over \code{Index Only Scan}. PostgreSQL sequential scans and
parallel gathers are disabled only in this mechanism-isolation experiment so
both engines retain a covering-index access path.

A second control builds one million identical ordinals as integer, eight-byte
string, and materialized-path-like long-string keys. PostgreSQL strings use
\code{COLLATE C}, matching the real table. Thirty range counts per key shape
are repeated five times. Finally, same-version MongoDB~7.0.34 and
PostgreSQL~16.14 profiling containers each hold one million long-string keys.
A single backend repeatedly counts the same 500{,}000-key range while CPU
sampling identifies the functions on each engine's per-key scan path.

\subsection{RQ2: Causal explanation}

We now intervene on the query while holding its bounds and order fixed.
\emph{Exact-output covered} returns
{\normalfont\code{(node\_id,title,summary)}} from a covering index. \emph{ID-only
covered} returns only {\normalfont\code{node\_id}}. Server-side
{\normalfont\code{EXPLAIN ANALYZE}} measurements use 40 row-count-stratified paths.
Both arms examine the expected number of index keys; MongoDB examines zero
documents and PostgreSQL performs zero heap fetches.

Table~\ref{tab:causal} shows that document or heap access is not required for
the gap: MongoDB remains 1.79$\times$ slower when both engines use zero-fetch
covering plans and return the exact output. The title/summary payload does not
explain the gap either: covered minus ID-only costs 7.4\,ms in MongoDB and
7.9\,ms in PostgreSQL.

Two narrower interventions locate the remaining mechanism. First, increasing
MongoDB's requested batch size removes one {\normalfont\code{getMore}} on average but
does not reduce latency in either the ID-only or exact-output arm. Second, both
engines return only a scalar count over all 200 original paths. MongoDB's
direct \code{count} command runs \code{COUNT} over \code{COUNT\_SCAN} with zero
documents examined; PostgreSQL is held to an index-only count with zero heap
fetches. MongoDB takes 7.4\,ms and PostgreSQL 4.3\,ms. Their fitted per-key
slopes are 0.190 and 0.112\,$\mu$s, respectively, and the five repetition
ratios remain between 1.69$\times$ and 1.81$\times$. The difference therefore
survives removal of document access, per-row output, per-row BSON payload, and
extra cursor round trips. Both engines still perform native count aggregation;
the experiment does not assume that PostgreSQL obtains the count for free.

MongoDB profiler records on representative 5k, 12k, and 100k-row ranges report
zero storage bytes read and zero storage-read time. For the ID-only covered
arm, mean server CPU time is 15.8\,ms and wall time is 15.3\,ms. The lean
MongoDB index is 280\,MB versus 877\,MB for PostgreSQL, so the result is not
explained by storage reads or a larger MongoDB index.

the base index-processing bottleneck; client record processing adds the
separate 5.3\,ms difference in Table~\ref{tab:breakdown}.

\section{Conclusion}

The two research questions have separate answers. For physical design,
Structure and Metadata should be colocated for this descendant-range workload:
doing so lowers P50 and P95 latency in MongoDB, PostgreSQL, and SQLite. For the
cross-engine comparison, document fetch, returned metadata, and an extra cursor
round trip cannot explain MongoDB's higher latency: the gap remains when both
engines scan the same logical index range and return only a count.
The direct-count path is 1.71$\times$ slower on the same 200 paths, and key-shape
controls show that long path strings are not the cause. PostgreSQL also advances
a B-tree cursor and runs an executor and aggregate. MongoDB's bottleneck is the
heavier per-key WiredTiger cursor/key-extraction and classic \code{COUNT\_SCAN}
bookkeeping path in the scalar control. Client record processing adds a further
5.3\,ms to the end-to-end difference.
