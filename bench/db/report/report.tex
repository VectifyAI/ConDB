\author{Junyao Dong}

\begin{abstract}
PageIndex stores documents as large hierarchical JSON trees that an agent
navigates from the root to relevant nodes. This report benchmarks storage-level
operations corresponding to ConDB retrieval on MongoDB, PostgreSQL/JSONB,
DuckDB, and SQLite, at scales up to ten million nodes. Schema effects and engine
effects are measured separately. In a matched three-million-node experiment,
MongoDB and PostgreSQL scan the same 200 subtree paths, return the same node ids,
and use equivalent covering indexes. On the monolithic layout, MongoDB is
$4.35{\times}$ slower at P50 and $3.91{\times}$ at P95; on narrow structure
stores, it is $4.65{\times}$ and $4.07{\times}$ slower. A MongoDB-specific
ten-million-node ablation shows that a lean covering index eliminates
document fetches and reaches $15.5$\,ms P50 / $168$\,ms P95. Together, these
results support covering the scan while leaving the full structure/metadata/text
split to an end-to-end deployment test.
\end{abstract}

\section{Introduction}

ConDB indexes a document as a PageIndex tree: a hierarchy of nodes carrying a
title, a summary, page indices, and (at the leaves) text. Retrieval is a
top-down traversal: the retriever starts at the root, lists a node's children to
decide where to descend, and fetches the content of selected nodes. ConDB also
exposes subtree access for tree formatting and utility paths. This report treats
its ids-only range scan as a storage stress microbenchmark rather than as a
replay of the complete retriever. Section~\ref{sec:prelim} presents the results,
the scan diagnosis, and the candidate schema; Section~\ref{sec:opt} specifies
its deployment validation.

The operation set follows ConDB's storage interface. Generic database operations
outside that interface (ancestor-to-root walks, page-range filters, naive
substring scans) are excluded.

\paragraph{Engines and setup.} MongoDB~7.0 (Community Edition) and
PostgreSQL~16 (JSONB document column) run as servers in Docker
over localhost; DuckDB and SQLite are embedded. The medium/large suite
runs on a 96-core Linux host with 1\,TB of RAM, using the same monolithic
one-record-per-node layout for cross-engine rows. The relational engines flatten
the tree to one row per node. Each read uses fixed seeded samples; every query is
checked to return the same row count. Each concurrency level runs its client
processes for five seconds. This host has ample memory, so reads are
cache-resident rather than disk-bound.

\paragraph{Subtree test sets.} The matched 3M experiment is the cross-engine
scan comparison: a clean 16-vCPU AMD EPYC 9K65 host with 30\,GiB RAM, a
three-million-node tree, and one engine per invocation. MongoDB and PostgreSQL
receive the same 200 seeded paths (average result: 8{,}840.4 ids) under three
matched configurations:
\emph{naive}, a monolithic store with a plain \code{path} index;
\emph{covered}, the same store with an equivalent covering index; and
\emph{narrow structure}, a separate structure relation with the same covering
index. PostgreSQL uses \code{(path) INCLUDE (node\_id)} followed by
\code{VACUUM ANALYZE} so \code{EXPLAIN} confirms a true index-only scan;
MongoDB uses \code{\{path,node\_id\}}, excludes \code{\_id} from projection,
and confirms \code{PROJECTION\_COVERED} with no \code{FETCH}. The 10M MongoDB
component measurements in Section~\ref{sec:solid} cover the larger tree. Unless
stated otherwise, subtree timings refer to the ids-only scan phase.

\paragraph{Execution model and comparability.} SQLite and DuckDB execute in
process, whereas MongoDB and PostgreSQL include localhost protocol overhead.
MongoDB--PostgreSQL is therefore the server-to-server latency comparison; the
embedded-engine measurements are contextual references. SQLite runs the same
three subtree configurations. DuckDB's columnar projection already reads only
\code{node\_id}, so the benchmark does not define independent covered or
narrow-structure measurements for it. Storage figures likewise reflect each
engine's native encoding and compression: MongoDB's \code{storageSize} is
post-compression, DuckDB uses columnar encoding, and PostgreSQL may compress
out-of-line values. MongoDB's logical BSON size is reported separately. Each
comparison is single-host within its own test series. The operations through
concurrency use one tree per database; multi-tenancy, batched reads, and deletion
use 25 co-resident trees.

\subsection{MongoDB subtree ID-scan diagnosis}\label{sec:diagnosis}

MongoDB's unit of read is the whole document. A secondary index (here on
\code{path}) is a separate B-tree holding only the indexed field and a record
id; to return any other field, the engine must \emph{fetch} the full BSON
document and apply the projection to it. A point lookup is one such fetch and is
cheap. A subtree scan over monolithic node documents---structure, \code{title},
\code{summary}, and leaf \code{text} in one document---is tens of thousands of
them, each reading and decoding the whole document no matter how small the
projection. The observed \code{FETCH} plan and
\code{totalDocsExamined} count confirm that path. With resident data and no
cache evictions, the measured cost is per-document work---locate the
record, materialize the document, project, stream through the cursor---times
subtree size. In the monolithic benchmark, the other primitives touch few
documents and remain fast.

Two controls isolate the cause on the ten-million-node tree (one measuring
client, resident collection, identical 200 seeded paths). Running 16, 32, or 64
background point-lookup processes leaves scan latency almost unchanged, with no
cache evictions. Removing the wide \code{text} field cuts each scanned document
by ${\sim}75\%$ but also leaves latency unchanged; even ${\sim}150$-byte
topology-only documents retain most of the cost. The dominant variable is the
number of fetches, which the candidate schema removes from the scan path
(Section~\ref{sec:solid}).

Row and column stores avoid this per-document work on the ID scan. A row store
materializes only the requested columns (PostgreSQL leaves the JSONB datum
compressed, since \code{node\_id} is its own column), and a column store reads
only the requested column, so both do far less per-node work on this one scan.
The monolithic measurements show inexpensive point, children, and content reads.
After metadata is decoupled, their complete cost may include an additional point
or batched read and remains part of the end-to-end schema test. The candidate
layout below isolates topology so the large ID scan can stay in the index.

\subsection{Candidate schema: decoupled structure and key-value
metadata}\label{sec:solid}

A node carries three kinds of data with different access patterns. The candidate
schema stores them separately:

\begin{itemize}\itemsep2pt
\item \textbf{Structure} (\code{node\_id}, \code{path}, \code{parent\_id},
  \code{depth}): ${\sim}150$-byte topology documents carrying a lean
  \code{\{tree\_id,path,node\_id\}} covering index. Serves the subtree ID scan
  and topology navigation.
\item \textbf{Metadata} (\code{title}, \code{summary}): a key-value collection
  keyed by \code{(tree\_id,node\_id)} (or an equivalently namespaced
  \code{\_id}). Serves rendered nodes by point or batched read.
\item \textbf{Text}: leaf body text in its own collection under the same
  tenant-qualified key.
  Serves \code{get\_entity} for the few nodes the model finally selects.
\end{itemize}

\begin{figure}[ht]
\centering
\includegraphics[width=0.92\linewidth]{figures/schema.pdf}
\caption{Candidate schema. A contiguous range of the
\code{\{tree\_id,path,node\_id\}} covering index returns tenant-qualified node
keys; those keys address metadata and text.}
\label{fig:schema}
\end{figure}

In the single-tree 10M MongoDB component test, the covered ID scan examines no
documents: \code{explain} reports \code{PROJECTION\_COVERED} and
\code{totalDocsExamined:\,0}, with $15.5$\,ms P50 / $168$\,ms P95
(Table~\ref{tab:solid}). Covered execution has two operational requirements.
First, the index must contain every projected field
and the projection must exclude \code{\_id}; otherwise the per-document
\code{FETCH} returns. Second, the covering index should be built after bulk load
so the write-once tree pays its maintenance cost once. Without coverage, even
the ${\sim}150$-byte structure documents run about $1.6{\times}$ slower.

The ids-only scan excludes the cost of rendering a tree view. The metadata row
resolves \emph{every} node of a large subtree using fixed 1{,}000-id batches and
costs ${\sim}1$\,s. Its ${\sim}36$ requests reflect that batch size rather than
MongoDB's 16\,MiB command limit; with this dataset's short ids, the complete BSON
command is about 0.62\,MiB. End-to-end latency should therefore be measured with
the formatter's actual fields, batching, and result bounds. If a deployment does need the full
\code{node\_id}+\code{title}+\code{summary} view from a single indexed query, the
alternative is to carry the metadata inside the covering index of a merged
collection: it stays covered and beats the monolithic scan, but the
multi-kilobyte \code{summary} key inflates that index to roughly the size of the
data itself, which is why the candidate schema keeps metadata in a key-value store
instead. Keep the anchored materialized-path range as the predicate either
way---an unanchored regex cannot form a range and must scan the whole index.

The measured component footprints are also smaller. For ten million nodes, the
single-tree structure collection occupies $0.28$\,GB of data plus $0.57$\,GB of
index, while the metadata store occupies $0.69$\,GB plus a $0.14$\,GB
\code{\_id} index. This ${\sim}1.7$\,GB navigation footprint compares with
$5.3$\,GB for the monolithic collection with inline \code{text}. The metadata
measurement uses \code{node\_id} as its single-tree key, so the tenant-qualified
index requires its own sizing. Whether the smaller footprint improves cache
residency under mixed navigation and content reads is measured by the
cache-constrained test in Section~\ref{sec:opt}.

\paragraph{Unmeasured structural extensions.} Nested Sets
or a tree-order \code{\_id} on a clustered collection turns the subtree into one
range query or a sequential read; a pre-computed subtree document turns it into a
point read. A write-once tree avoids steady-state renumbering or rewrite costs,
but these designs add ingest work and storage amplification. Their value depends
on the complete retrieval path and must be measured before adding schema
complexity.

\section{Deployment validation plan}\label{sec:opt}

The structure scan and metadata stress case in Section~\ref{sec:solid} were
measured on a cache-resident host; the complete three-store path was not. A
production deployment also adds the opposite constraint: many trees or tenants can
make the working set larger than RAM, so the plan must also keep the hot
navigation data in cache. The candidate validation plan is therefore:

\begin{enumerate}\itemsep2pt
\item \textbf{Validate the decoupled schema end to end.} Structure
  (\code{tree\_id}, \code{node\_id}, \code{parent\_id}, \code{depth},
  \code{path}) in the navigation collection; \code{title} and \code{summary} in
  a key-value metadata collection keyed by \code{(tree\_id,node\_id)}; body text
  in a third collection under the same key. Table~\ref{tab:solid} measures the
  covered structure component. The complete path, including tenant-qualified
  keys, metadata resolution, and formatting, requires an end-to-end measurement.
\item \textbf{Lead tenant-local query indexes with \code{tree\_id}.} Point,
  children, subtree, and content reads should use compound indexes beginning with
  \code{tree\_id}, preserving selectivity as the number of trees grows. A shard
  key may use the same prefix, but its final form must also account for tenant
  size and write distribution.
\item \textbf{Keep the covering index lean and exactly aligned with the
  projection.} A \code{\{tree\_id,path,node\_id\}} index serves subtree ID scans
  index-only; build it after bulk load so its maintenance cost is paid once.
  Covered execution is all-or-nothing---a missing projected field, or \code{\_id}
  left in the projection, silently brings the per-document \code{FETCH} back---so
  treat \code{explain} showing \code{totalDocsExamined:\,0} as a deployment
  check, not a one-time observation. Do not put the multi-kilobyte \code{summary}
  into the covering key: the metadata store is intended to serve it separately, and
  carrying it in the index costs index bytes comparable to the data itself.
\item \textbf{Denormalize hot subtree views only after measuring demand.} If
  endpoint profiling identifies subtree rendering as a top latency contributor,
  use write-once structure
  to precompute bounded structure+summary subtree views, or add Nested Sets /
  tree-order \code{\_id} for range-locality. These remove even the covered scan's
  per-key work, but they add storage amplification and more complicated ingest.
\end{enumerate}

\noindent The required cache test compares the decoupled schema with a
monolithic inline-text layout while sizing the WiredTiger cache below the
monolithic working set and above the decoupled navigation working set. This
directly measures the residency benefit that a fully cache-resident run cannot
show.

\section{Conclusion}

The results separate the value of the index from the remaining engine gap. In
the matched 3M experiment, covering improves MongoDB from 2.391/19.201\,ms to
1.291/10.692\,ms P50/P95. PostgreSQL with equivalent coverage reaches
0.297/2.732\,ms, making MongoDB $4.35{\times}$ slower at P50 and
$3.91{\times}$ at P95. Moving the covered scan to a narrow structure store adds
little warm-cache benefit on either engine; the corresponding MongoDB/PostgreSQL
ratio is $4.65{\times}$/$4.07{\times}$. These figures describe the ids-only scan,
not the complete retrieval endpoint.

MongoDB's document read path explains the optimization: a non-covered scan pays
per matched document regardless of projection, whereas the covering index keeps
the ID scan in the B-tree. Decoupling structure from metadata and text may also
reduce the navigation footprint, but that benefit depends on the complete access
pattern. The 10M MongoDB result of
$15.5$\,ms/$168$\,ms provides the larger-scale capacity point. A deployment
decision still requires the cache-constrained layout comparison and a complete,
tenant-qualified structure/metadata/text measurement using the formatter's real
fields and result bounds.
