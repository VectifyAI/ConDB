\title{\textbf{Storage Engines for PageIndex Retrieval:\\ A Workload-Grounded
Benchmark of MongoDB, PostgreSQL, DuckDB, and SQLite}}
\author{Junyao Dong}
\date{}

\begin{document}
\maketitle

\begin{abstract}
PageIndex turns documents into large hierarchical JSON trees that an agent
navigates from the root to the relevant nodes. We benchmark four storage engines
(MongoDB, PostgreSQL/JSONB, DuckDB, and SQLite, ConDB's current engine) on the
exact operations ConDB's retrievers issue against storage, at scales up to ten
million nodes. Across navigation reads, content fetch, writes, concurrency, and
storage footprint, MongoDB is competitive on every operation except one:
fetching a large subtree (\code{get\_subtree}), a materialized-path range scan
matching tens of thousands of nodes. The initial benchmark recorded a multi-second
P95 there, but a controlled re-measurement---in isolation and under concurrent
load, with the collection fully resident in cache---finds a stable P95 of roughly
$0.4$\,s, about $3{\times}$ PostgreSQL rather than the order of magnitude the first
run suggested; the seconds-level figure was a contention artifact of the
concurrent multi-engine run, not a steady-state cost. We trace the remaining gap to
MongoDB's document-at-a-time read model: each matched node is a separate
\code{FETCH}, so the cost tracks the number of nodes in the subtree. We also
measure fixes on Community Edition (Section~\ref{sec:opt}): because the cost is the
\emph{number} of fetches, only removing them helps, and only modestly---a covering
index buys ${\sim}1.4{\times}$---since the sub-second baseline leaves little to gain.
\end{abstract}

\section{Introduction}

ConDB indexes a document as a PageIndex tree: a hierarchy of nodes carrying a
title, a summary, page indices, and (at the leaves) text. Retrieval is a
top-down traversal: the retriever starts at the root, lists a node's children to
decide where to descend, pulls a subtree for the language model to read, and
fetches the content of the nodes it selects. The project question is whether a
document store (MongoDB) is the right home for this data and, if so, what to
optimize. This report answers both with measurements, including a measured
optimization plan for the one weak spot (Section~\ref{sec:opt}).

We deliberately benchmark only the operations ConDB actually issues. Generic
database operations that the retrieval path never performs (ancestor-to-root
walks, page-range filters, naive substring scans) are excluded, because their
results would not inform the optimization.

\paragraph{Engines and setup.} MongoDB~7.0 (Community Edition) and
PostgreSQL~16 (JSONB document column) run as servers in Docker
over localhost; DuckDB and SQLite are embedded. All engines run on the same
96-core Linux host with 1\,TB of RAM. Every engine stores one record
per node with identical logical fields and the indexes each query needs. The
tree is flattened to one row per node; \code{get\_subtree} uses a materialized
path with a byte-order range predicate, identical across engines (PostgreSQL's
\code{path} column uses \code{COLLATE "C"} so its range matches the others'
binary comparison). The subtree query returns node ids; adding the title and
summary the tree view also renders would cost the relational engines more but not
MongoDB, whose non-covering \code{FETCH} already reads the whole document, so
adding fields to the projection costs it nothing---making this choice conservative
toward MongoDB. Each read is measured over 500 sampled
nodes (200 subtree roots, drawn at depth ${\le}3$), fixed by seed and identical
across engines; every query was checked to return the same row count on all
four engines. Each concurrency level runs its client processes for five
seconds. The host has ample memory, so every engine's data is cache-resident
and reads are not disk-bound.

\paragraph{Fairness caveats.} SQLite and DuckDB run in-process, so a query is a
function call; MongoDB and PostgreSQL pay per-call client--server overhead (a
localhost round trip plus protocol handling) that the embedded engines never
incur. The fair single-call comparison is therefore MongoDB versus
PostgreSQL; absolute microseconds across the embedded/server line are not
comparable, and the concurrency section (independent processes, no GIL) shows
real server throughput. MongoDB's \code{storageSize} is post-compression
(WiredTiger snappy); the others are uncompressed on-disk files, so MongoDB's
uncompressed logical size is reported separately, and the random-word content
likely compresses better than real prose, flattering the compressed figure.
All measurements are single-host. The operations through concurrency use one
tree per database; multi-tenancy, batched reads, and deletion are measured
separately below on 25 co-resident trees.

\section{Why MongoDB trails on \code{get\_subtree}}

The cause is structural, not a configuration mistake. MongoDB's unit of read is
the whole document. A secondary index (here on \code{path}) is a separate
B-tree holding only the indexed field and a record id; to return any other
field, the engine must \emph{fetch} the full BSON document and apply the
projection to it. A point lookup is one such fetch; a large subtree is tens of
thousands, the biggest in the workload far more. The data is cache-resident
(and pages in the WiredTiger cache are stored uncompressed), so the cost is
neither disk I/O nor decompression: the time goes to per-document work. Because
the \code{path} index is non-covering, each matched record id triggers a
\code{FETCH} of the whole BSON document---\code{text} payload and all, even though
the query needs only a node id---and tens of thousands of those fetches batch
through the cursor. Multiplied by subtree size, that per-document overhead is the
cost of the operation. The other operations touch few documents, so they stay fast.

The cost therefore scales with the number of nodes in the subtree: the largest
subtrees, near the root, are the slowest. How large that tail actually is---and
whether the original run's multi-second figure is a steady-state property or an
artifact of that run's contention---is the subject of the next section.

The row and columnar engines do less work per node. A row store visits each
matching row but materializes only the requested column; the wide \code{text}
sits unread in the row (PostgreSQL does not even decompress the JSONB datum,
since \code{node\_id} is a separate column). A column store reads only the
requested column in vectorized batches. Both could go further still with a
covering index that answers the range from the index alone (Section~\ref{sec:opt}).
All of these do far less per-row work than a per-document fetch.

This is the price of the document model, and it is also why MongoDB wins
elsewhere: storing all of a node's fields together makes ``fetch one whole
entity'' fast (point and children reads), in-place field updates cheap (the
write path), the layout shard-friendly (concurrency), and the on-disk form
compact (storage). MongoDB is optimized for a different access pattern, and the
PageIndex workload plays to it on every operation but one.

\section{Re-measuring the tail}\label{sec:remeasure}

The original \code{get\_subtree} figure (P95 2478\,ms) was recorded while the other
three engines, the write benchmark, and the concurrency sweep ran on the same host.
To separate the query's own cost from that contention, we re-measured it on the
ten-million-node tree under controlled conditions: one measuring client, the
collection freshly loaded and fully resident, the same 200 seeded subtree paths.

Re-measured in isolation, P95 is ${\sim}0.30$--$0.42$\,s (P50 ${\sim}30$--$40$\,ms),
stable across repeated runs---an order of magnitude below the first run. Driving the
same query while 16, 32, then 64 concurrent processes hammer point lookups at the
same \code{mongod} barely moves it (Table~\ref{tab:remeasure}): P95 rises from $331$
to $376$\,ms across the sweep, $1.1{\times}$, never approaching seconds. Throughout,
the WiredTiger cache holds the whole collection (${\sim}17$\,GB resident in a
$540$\,GB cache) and reports zero application-thread evictions---so the tail is
neither eviction nor, as it turns out, ordinary read contention.

whole-system resource contention, or a cold-cache first touch before the collection

still holds (each matched node is a separate \code{FETCH}, so cost grows with subtree
size), but its steady-state magnitude is sub-second.

\section{Is MongoDB the wrong tool?}

The introduction asked whether a document store is the right home for this data,
and \code{get\_subtree} is where the question bites: a relational or columnar engine
does this operation natively, reading one column and never touching the \code{text}
blob, which is why PostgreSQL posts a ${\sim}123$\,ms tail to MongoDB's ${\sim}0.4$\,s
(Section~\ref{sec:remeasure}). On the bare operation the relational model is the
better fit, and this report does not pretend otherwise.

But the gap is ${\sim}3{\times}$ on a sub-second, infrequent operation---not the order
of magnitude the first run implied---and it sits against MongoDB's wins on every
other operation the workload issues: point, children, and content reads;
vacuum-free updates; concurrency; footprint. Three workload facts keep it in
proportion. The subtree view needs only \code{node\_id}, \code{title}, and
\code{summary}, never the large \code{text}. The tree is largely write-once after
ingest. And the largest subtrees sit near the root, which a top-down traversal
pulls at most once or twice per query before descending into progressively smaller,
faster ones. The verdict is conditional but, for \emph{this} workload, clear: a
${\sim}3{\times}$ tail on the one projection-heavy scan does not outweigh MongoDB's
advantages elsewhere.

\section{Optimizing \code{get\_subtree}}\label{sec:opt}

even that is modest because the steady-state baseline is already sub-second.

\subsection{What the measurements say}

\paragraph{Splitting the \code{text} field does nothing.} The intuitive fix---move
the large \code{text} into a separate collection so the scanned documents are
small---was the leading hypothesis, and it is wrong here. It shrinks the collection
by ${\sim}75\%$ ($4.97\to1.25$\,GB) yet leaves \code{get\_subtree} P95 unchanged
($419\to419$\,ms). The reason is the cache: at $540$\,GB it holds the whole
collection many times over (Section~\ref{sec:remeasure}), so document \emph{size}
never gates the scan---document \emph{count} does. Each of the ${\sim}36$k matched
nodes is a separate \code{FETCH}, and shrinking each one does not reduce their
number. The Subset Pattern's premise---a working set too large for RAM---does not
hold on this host.

\paragraph{A covering index is the only real lever, and a modest one.} Removing the
\code{FETCH} is the one thing that helps. A lean \code{\{path,node\_id\}} index
serves the id-only subtree query index-only (\code{explain} confirms
\code{PROJECTION\_COVERED}, \code{totalDocsExamined:\,0}) for ${\sim}1.4{\times}$. But
the tree view also needs \code{title} and \code{summary}: extending the index to
cover them works (${\sim}1.2{\times}$) yet inflates it to $4.66$\,GB---as large as the
collection's own data---because \code{summary} is a multi-kilobyte key, confirming
the fat-key concern. Resolving the view with a covered id scan plus a batched
\code{\$in} is worse, not better (${\sim}3{\times}$ slower): a ${\sim}36$k-id
\code{\$in} overflows the 16\,MB command limit (forcing ${\sim}36$ chunked round
trips) and re-fetches the same documents anyway. Keep the anchored
materialized-path range as the predicate---an unanchored regex cannot form a range
and must scan the whole index---and treat cache sizing and \code{zstd} as
irrelevant here: the data is already resident, so neither touches the per-fetch cost.

\paragraph{A larger win needs structural denormalization, untested here.} Nested
Sets or a tree-order \code{\_id} on a clustered collection turns the subtree into one
range query or a sequential read; a pre-computed subtree document turns it into a
point read. All are viable precisely because the tree is write-once (their cost is
paid once at ingest), and all remove fetches wholesale rather than shrinking them.
We did not measure them: with the baseline already at ${\sim}0.4$\,s, the open
question is whether the schema complexity is worth shaving a sub-second, infrequent
operation. (\code{\$graphLookup} is not a candidate---it re-traverses
\code{parent\_id}, still materializes documents, and in 7.0 is capped at 100\,MB and
ignores \code{allowDiskUse}.)

\subsection{What will not help}

\paragraph{A newer MongoDB version does not close the gap.} Upgrading the engine
does not fix this without a schema change. Against this operation---a
projection-heavy range scan over ordinary documents---the 8.0--8.3 line offers
nothing: the 8.0 \emph{Express} path is a point/equality fast path on a single
index (\code{\_id}-style, no range, sort, or skip), 8.0 \emph{block processing}
is scoped to time-series collections, and the \code{\$graphLookup} disk-spill fix
(SERVER-23980) lands only in 8.2.0 (reverted from 8.1) and only helps the
recursive alternative anyway. The document-at-a-time \code{FETCH} is unchanged
across the line.

\paragraph{What Community Edition does not offer.} The feature that would fix this
most cleanly---a column-store index, so a projection-heavy scan reads only the
projected column, as the relational engines do---is Atlas-only. But PageIndex never
scans the whole corpus, so a column store solves a problem this workload does not
have; the schema fixes above address the one it does. Self-managed Search and
Vector Search run on Community since 8.2 (a separate \code{mongot} process, public
preview, replica set required) but serve relevance retrieval, not a
range-projection scan. No Atlas- or Enterprise-only feature addresses the
document-at-a-time read model itself, so the only levers are schema, index, and
storage configuration---all on Community.

\subsection{What remains open}

Two things the measurements did not pin down. First, the exact origin of the
original 2478\,ms---whole-system contention during the multi-engine run, or a
cold-cache first touch before the collection was warm; point-lookup contention alone
does not reproduce it (Section~\ref{sec:remeasure}), so the cause is heavier than the
concurrency the workload itself generates. Second, the measured payoff of the
structural-denormalization options above. Neither changes the practical conclusion:
\code{get\_subtree} is a sub-second, ${\sim}3{\times}$-PostgreSQL operation whose only
cheap fix---a covering index---has limited upside.

\section{Conclusion}

For the PageIndex retrieval workload, MongoDB is competitive on point and children
reads and content fetch, accumulates no dead-tuple bloat under updates (no vacuum
debt), has a compact footprint, and scales monotonically under concurrency with the
lowest tail latency of the server engines (though not their highest absolute
throughput). Its one relative weakness is \code{get\_subtree}: a controlled
re-measurement puts its steady-state P95 at ${\sim}0.4$\,s, roughly $3{\times}$
PostgreSQL and ${\sim}3{\times}$ at the median too---not the multi-second tail the
first run recorded, which we trace to contention rather than to the query. The cost
is the per-node \code{FETCH} count, which tracks the number of nodes in the
subtree. The practical reading: \code{get\_subtree} is the one place MongoDB trails,
the gap is ${\sim}3{\times}$ on a sub-second, infrequent operation, and not a reason
against MongoDB for this workload. Its optimization space is narrow: because the
cost is the \emph{number} of per-node fetches, only removing them helps, and a
covering index---the one cheap lever---buys just ${\sim}1.4{\times}$ (Section~\ref{sec:opt}).
