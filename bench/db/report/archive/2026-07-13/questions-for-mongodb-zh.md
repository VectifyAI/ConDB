# 给 MongoDB 的问题

## 背景

我们把文档存成大的层级树:一个节点一个 document,字段有 `node_id`、`title`、`summary`、
一个 materialized path 字符串、`parent_id`、`depth`,叶子上还有一个很大的正文字段。树有
几百万节点,能轻松装进内存。我们关心的读操作是"拉一整棵子树的结构":用 path 区间扫描命中
最多几万个节点,只返回小字段(`node_id`/`title`/`summary`)来渲染树视图;正文是之后单独读,
而且只读被选中的少数节点。树在导入后基本只读不写。

调优我们自己来。下面这些是文档讲不清、想听你们判断的点。文档里已经讲明白的(Subset 模式、
精简覆盖索引、几种树建模、前缀压缩、自管版没有列式/covered-scan)我们就不问了。

## 问题

**1.** 在 7.0(classic 引擎,7.0.17 起 SBE 默认关闭)上,如果查询通过索引命中很多文档,却
只投影几个小字段,`FETCH` 是不是仍然把每条整文档(包括我们没要的那个大字段)读出来、解码完,
再丢掉?文档没写清楚。到了 8.0 的 SBE 会不会变,能不能跳过那个没被投影的大字段、根本不读?

**2.** 我们打算把大正文字段挪到单独的集合,树视图这条读用一个只含小字段的覆盖索引来服务。
这个思路成立吗?还是说数据全在缓存里之后,命中一大批时逐文档的 `FETCH` 才是大头,拆字段对
这条读其实没意义?

**3.** 对一棵只写一次、几百万节点的树,热读要拉一整棵子树的结构(给最多几万个节点取小字段),
你们在实际生产里见过这种访问模式吗?建模我们自己来,想要的是这种体量的大树视图在 MongoDB 上的
案例或参考部署,以及那些团队最后用的是哪种方案。
