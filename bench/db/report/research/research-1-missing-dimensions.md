## 研究问题
We wrote a storage-engine benchmark report (MongoDB 7.0 Community vs PostgreSQL 16 JSONB vs DuckDB vs SQLite) for a specific workload: an agentic RAG system ("PageIndex"/ConDB) that stores documents as large hierarchical trees (up to 10M nodes, one row/document per node with title, summary, materialized path, and large text payloads) and retrieves by top-down LLM-guided traversal. The report benchmarks: point lookup by id, fetch children of a node, fetch subtree via materialized-path range (~36k rows), fetch node content, bulk ingest, single-field updates, incremental inserts, point-lookup concurrency scaling across client processes, and on-disk footprint. The audience is MongoDB staff evaluating whether MongoDB should be the storage engine.

Research question: What important storage operations or benchmark dimensions is this report MISSING that (a) database benchmarking literature/practice considers essential for credible engine comparisons, and (b) are specifically relevant for agentic-RAG / hierarchical-document-tree workloads and for a MongoDB-staff audience?

We already know from auditing our own code that these exist but were not benchmarked: batched multi-get by id list (SQL IN-list chunks of 500, on MongoDB this would be $in), children-fetch joined with content payloads (LEFT JOIN nodes-entities; on MongoDB $lookup or embedded), a MAX(depth) aggregate per tree, tree deletion, and listing/metadata queries. Evaluate how much each of those matters for a MongoDB-vs-relational comparison.

Beyond those, specifically investigate and assess relevance of: (1) vector/embedding search and full-text search (MongoDB Atlas Search vs community edition options; pgvector/FTS in PostgreSQL) since RAG systems commonly add these; (2) mixed read/write concurrent workloads (readers + writers simultaneously) vs our pure-read concurrency test; (3) cold-cache / disk-bound performance vs our fully cache-resident setup; (4) multi-tenancy (many trees in one database, selectivity) which we noted as not exercised; (5) deletes and space reclamation (delete_tree); (6) batched $in reads on MongoDB — known performance characteristics vs point reads; (7) MongoDB-specific capabilities its staff would expect a fair report to mention: aggregation pipeline with $graphLookup for tree traversal, covered queries/covering-index constraints in MongoDB (when projections can be served index-only, limits on index key size), $lookup performance, change streams, transactions across documents; (8) standard benchmark methodology critiques (YCSB and similar): warm-up, run length, coordinated omission in latency measurement, number of repetitions/variance reporting.

Deliverable: a prioritized list of missing operations/dimensions, each with: why it matters for this workload, whether it would likely change the report's conclusion (MongoDB competitive everywhere except large-subtree fetch, fixable with covering index + splitting text into a separate collection + nested subtree documents), and concrete sources. Also flag any claims in our optimization plan that the literature contradicts — especially whether MongoDB covered queries can really serve path+node_id+title+summary index-only (index key size limits, can summaries be in an index?), and whether splitting text into a separate collection is established practice (subset/extended-reference patterns).

## 综述
The verified literature identifies two genuinely missing benchmark dimensions that are load-bearing for the report's conclusion: (1) a cold-cache/disk-bound run, required both by fair-benchmarking methodology (Raasveldt et al., DBTest'18) and by MongoDB's own docs — the proposed text-split (Subset Pattern) optimization's documented benefit operates through working-set/RAM reduction, so a fully cache-resident benchmark structurally cannot demonstrate it; and (2) a children-fetch-joined-with-content benchmark comparing $lookup against an embedded/idiomatic schema, since MongoDB's manual classifies frequent $lookup as a schema anti-pattern, meaning the current omission hides a known MongoDB weak spot while also denying MongoDB its recommended embedded design. On the optimization plan itself, the literature largely validates rather than contradicts it: splitting large text into a separate collection is MongoDB's named, vendor-sanctioned Subset/Extended Reference pattern, and a path+node_id+title+summary covering index is mechanically possible in MongoDB 7.0 (the historical 1024-byte index key limit was removed in 4.2 and the v7.0 limits page contains no per-entry byte cap) — but covered execution demands a single compound index containing all four fields plus an explicit _id:0 projection, and MongoDB's stated rationale for covered-query speed (small, RAM-resident keys) is undermined by multi-KB summaries in index keys, so the benefit is unproven. The nested-subtree-document idea is hard-bounded by the 16 MiB BSON cap (a ~36k-node subtree at the measured ~581 B/node is ~20.9 MB) and must be bucketed or use GridFS. Finally, a fair MongoDB subtree benchmark should use the documented anchored-prefix-regex materialized-path idiom on an indexed path field, and the report should acknowledge MongoDB's documented Nested Sets pattern as the purpose-built fix for subtree fetch on static (write-once-after-ingest) trees.

## 已验证结论(Findings)

### [1] PRIORITY 1 — Missing dimension: cold-cache / disk-bound benchmarking. Credible benchmark methodology requires reporting cold and hot runs separately, and MongoDB's documented rationale for the Subset Pattern (the report's own proposed text-split fix) operates through working-set/RAM reduction and reduced disk access — a regime the fully cache-resident benchmark never enters. The report therefore cannot measure the main advantage of its own proposed optimization, and a MongoDB-staff audience evaluating the Subset Pattern fix would find hot-only numbers non-probative.
- **置信度**:high · **投票**:3-0, 3-0, 3-0 (merged from 3 claims)
- **证据**:DBTest'18 (Raasveldt et al., 'Fair Benchmarking Considered Difficult'), Section 3.5: 'the performance measurements made for cold and hot runs should be gathered and reported separately'; its Appendix A checklist makes cold/hot separation a requirement. MongoDB Subset Pattern docs: 'By using smaller documents with more frequently accessed data, you reduce the overall size of the working set. This allows for shorter disk access times'; the companion blog: 'When the working set of data and indexes grows beyond the physical RAM allotted, performance is reduced as disk accesses starts to occur.' All three underlying claims verified verbatim against primary sources. Caveat noted by verifiers: large documents also carry in-RAM costs (BSON deserialization, wire bytes), so a warm-cache run could show some text-split benefit, but the vendor-documented main mechanism is untestable cache-resident.

  - https://www.mongodb.com/docs/manual/data-modeling/design-patterns/group-data/subset-pattern/
  - https://www.mongodb.com/company/blog/building-with-patterns-the-subset-pattern

### [2] PRIORITY 2 — Missing operation: children-fetch joined with content payloads ($lookup vs embedded). MongoDB's manual officially classifies frequent $lookup as a schema design anti-pattern ('can be slow and resource-intensive compared to operations that only query a single collection') and recommends restructuring into a single collection; the Extended Reference pattern blog frames reducing JOINs as the performance win. Omitting this operation both hides a known MongoDB weak spot under the report's normalized row-per-node schema AND denies MongoDB its idiomatic embedded design — a fair comparison should benchmark an embedded schema variant, not only normalized rows. This could change the report's conclusion in either direction, and the outcome is empirically non-obvious because MongoDB 6.0+'s slot-based execution engine substantially improved eligible $lookup stages.
- **置信度**:high · **投票**:3-0, 3-0, 3-0 (merged from 3 claims)
- **证据**:Manual anti-pattern page verified verbatim: 'While the $lookup operation is useful when used infrequently, it can be slow and resource-intensive compared to operations that only query a single collection. If you often use $lookup operations, consider restructuring your schema to store related data in a single collection.' Extended Reference blog: 'performance is improved... through faster reads and a reduction in the overall number of JOINs.' A per-traversal-step children+content join in an LLM-guided traversal is squarely 'frequent use.' Verifiers confirmed the anti-pattern guidance remains in the current (2026) manual despite SBE improvements, and that Atlas schema advisors actively flag $lookup-heavy workloads.
- **来源**:
  - https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/reduce-lookup-operations/
  - https://www.mongodb.com/company/blog/building-with-patterns-the-extended-reference-pattern
  - https://www.mongodb.com/docs/v7.0/reference/sbe/

### [3] OPTIMIZATION-PLAN CHECK (validated on feasibility): a path+node_id+title+summary covering index is mechanically possible in MongoDB 7.0. The v7.0 Limits and Thresholds page contains NO per-index-entry byte-size limit — the historical 1024-byte index key cap was removed in MongoDB 4.2 (fCV >= 4.2) and does not appear anywhere on the current or v7.0 limits pages — and none of the documented covered-query restrictions (multikey/array fields, geospatial indexes, shard-key requirement on mongos) blocks a covering index on scalar string fields in an unsharded Community deployment. Large summary text fields CAN be index keys.
- **置信度**:high · **投票**:3-0, 3-0, 3-0 (merged from 3 claims)
- **证据**:Verifiers fetched both limits pages and grepped raw HTML plus stripped text: zero hits for 'Index Key Limit', 'index entry', or a 1024-byte cap (all '1024' matches were CSS media queries); only count-based index limits exist (64 indexes/collection, 32 fields per compound index, 100,000 generated keys/document). Removal in 4.2 corroborated via archived pre-4.2 docs and 4.2 release-notes language. Covered-query restrictions verified verbatim on the v7.0 page: 'Multikey indexes cannot cover queries over array fields... Geospatial indexes can't cover a query... When run on mongos, indexes can only cover queries on sharded collections if the index contains the shard key' — none applies to scalar path/node_id/title/summary unsharded.
- **来源**:
  - https://www.mongodb.com/docs/v7.0/reference/limits/
  - https://www.mongodb.com/docs/manual/reference/limits/

### [4] OPTIMIZATION-PLAN CHECK (qualified — benefit contradicted in spirit, not mechanics): covered execution has strict conditions and its documented performance rationale breaks with fat keys. (a) Every predicate field AND every returned field must be in ONE compound index (index intersection cannot produce covered queries), so all four fields including summary must share a single index. (b) The projection must explicitly specify _id: 0 (unless _id is in the index) — a benchmark that projects node fields without suppressing _id gets a FETCH stage, not index-only execution, confirmed by explain plans (PROJECTION_COVERED with totalDocsExamined: 0 only with _id: 0). (c) MongoDB's stated reason covered queries are fast — 'Index keys are typically smaller than the documents they catalog, and indexes are typically available in RAM' — is undermined when multi-KB summaries become index keys: index bloat and cache pressure may erase the win. No source confirms a fat covering index actually beats document fetches; the report's fix is feasible but its speedup is an untested hypothesis.
- **置信度**:high · **投票**:3-0, 3-0, 3-0, 3-0 (merged from 4 claims)
- **证据**:Manual verified verbatim: 'A covered query... doesn't have to examine any documents. An index covers a query when... All the fields in the query... are part of an index [and] All the fields returned in the results are in the same index'; 'the projection document must explicitly specify _id: 0... since the index does not include the _id field' (identical in v7.0 manual). Index-intersection docs confirm intersection applies only to predicates, never projections. Performance rationale quote verified in the 'Run Covered Queries' section. A MongoDB-org-published explain-plan demonstration (Pachot, dev.to/mongodb) empirically confirms the _id: 0 requirement across 7.0-8.3. Additional unverified-but-documented conditions: no null-equality predicates.
- **来源**:
  - https://www.mongodb.com/docs/manual/core/query-optimization/
  - https://www.mongodb.com/company/blog/performance-best-practices-indexing
  - https://www.mongodb.com/docs/v6.0/core/index-intersection/

### [5] OPTIMIZATION-PLAN CHECK (hard constraint): the 16 MiB BSON document cap bounds the 'nested subtree documents' fix. MongoDB 7.0 enforces a hard 16 MiB maximum per document ('To store documents larger than the maximum size, MongoDB provides the GridFS API'), and the report's own measured ~581 B average per node (bench/db/RESULTS.md line 53) puts a ~36k-node subtree with text payloads at ~20.9 MB — over the limit. The optimization must therefore be bucketed (structure+summary subdocuments of a few levels, text split out) rather than one document per subtree; a 100-level BSON nesting limit is a second independent bound. MongoDB has stated it will not raise the limit.
- **置信度**:high · **投票**:3-0, 3-0 (merged from 2 claims)
- **证据**:Both limits pages verified verbatim: 'The maximum BSON document size is 16 mebibytes.' Verifier arithmetic: 36,000 nodes x 581 B = ~20.9 MB > 16.78 MB; only ~470 B/node average is needed to exceed the cap given the entity schema in /home/junyao/code/pageindex/ConDB/bench/db/bench_operators.py. MongoDB's feedback portal (suggestion 45455761) confirms the limit is not configurable and will not be raised (48 MB wire-protocol constraint). The report's RESULTS.md already partially acknowledges this ('a full-text subtree would exceed the limit several times over'), so the finding confirms rather than contradicts — but the final report must present the optimization as bucketed, never as one-document-per-subtree.

### [6] OPTIMIZATION-PLAN CHECK (validated): splitting large text payloads into a separate collection while keeping title/summary/path co-located is established, vendor-named MongoDB practice, not an ad-hoc hack. It is MongoDB's official Subset Pattern ('split your collection into two collections: one for your most accessed data, and one for your least accessed data'), reinforced by the Extended Reference pattern (embed only highest-priority, most frequently accessed fields) and by Atlas schema suggestions ('Reduce the Size of Large Documents'), whose worked example is structurally identical to the proposed node/text split. Citing the Subset Pattern manual page (partition form) plus Extended Reference makes the report's framing airtight for a MongoDB-staff audience.
- **置信度**:high · **投票**:3-0, 3-0, 3-0, 3-0 (merged from 4 claims)
- **证据**:Four independently verified vendor sources, all verbatim: manual Subset Pattern page ('split your collection into two collections...'); 2019 patterns blog ('the most used part of the document should go into the main collection and the less frequently used data into another'); Extended Reference blog ('we only embed those fields of the highest priority and most frequently accessed'); and the anti-pattern page naming 'the subset schema design pattern' as the recommended remedy. Pattern present in current (8.3) manual, Atlas schema advisor, and the M320 data-modeling course — current, not stale 2019 content. Documented trade-offs to carry into the report: managing two collections, extra queries when full text is needed, consistency if fields are duplicated.
- **来源**:
  - https://www.mongodb.com/docs/manual/data-modeling/design-patterns/group-data/subset-pattern/
  - https://www.mongodb.com/company/blog/building-with-patterns-the-subset-pattern
  - https://www.mongodb.com/company/blog/building-with-patterns-the-extended-reference-pattern
  - https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/reduce-lookup-operations/

### [7] BENCHMARK-FAIRNESS CHECK: the MongoDB subtree-fetch benchmark should use MongoDB's documented materialized-paths idiom — an anchored prefix regex (e.g. find({path: /^,Books,/})) on an indexed path field — and the docs state a single-field path index 'improves the query performance significantly' for rooted subtree queries, supporting the plan's index-the-path premise. Anchored case-sensitive prefix regexes are converted into index range bounds internally, so the difference vs the SQL engines' byte-range scan is query idiom, not execution strategy. However, the tree-structure docs discuss the path index only for filtering and say nothing about serving title/summary payloads index-only — the covering half of the fix has no support from this source.
- **置信度**:high · **投票**:3-0 (regex idiom); 2-1 (path-index sub-claim)
- **证据**:Tutorial page verified verbatim: 'db.categories.find( { path: /^,Books,/ } )' and 'For queries from the root Books sub-tree (e.g. /^,Books,/ or /^,Books,Programming,/), an index on the path field improves the query performance significantly'; $regex docs confirm left-anchored prefix expressions execute as index range scans. Note: the regex-idiom claim passed 3-0; the path-index-performance sub-claim passed 2-1, with the dissent centered on citation precision (quote lives on the tutorial sub-page, not the cited overview page) rather than substance — three near-duplicate claims citing the tutorial URL directly were refuted 0-3, apparently on duplication/citation grounds, so the final report should cite both URLs carefully.
- **来源**:
  - https://www.mongodb.com/docs/manual/applications/data-models-tree-structures/
  - https://www.mongodb.com/docs/manual/tutorial/model-tree-structures-with-materialized-paths/
  - https://www.mongodb.com/docs/manual/reference/operator/query/regex/

### [8] MISSING SCHEMA VARIANT: MongoDB's documented Nested Sets pattern is the purpose-built fix for exactly the one operation where MongoDB lost (large-subtree fetch) — 'a fast and efficient solution for finding subtrees' via a left/right range query — at the cost of tree mutability, recommended 'for static trees that do not change.' PageIndex trees are effectively write-once after ingest (renumbering is per-tree, so new trees and single-field updates don't disturb existing structure), so MongoDB staff would reasonably expect the report to evaluate or at least mention this documented alternative before concluding MongoDB needs the covering-index workaround. Tension to disclose: the report's incremental-insert benchmark conflicts with nested sets' costly structural mutation.
- **置信度**:high · **投票**:3-0
- **证据**:Verified verbatim on the v7.0 manual (the exact benchmarked version) and the current 8.3 manual: 'The Nested Sets pattern provides a fast and efficient solution for finding subtrees but is inefficient for modifying the tree structure. As such, this pattern is best for static trees that do not change.' The doc's example confirms subtree retrieval is a pure range query: find({left: {$gt: ...left}, right: {$lt: ...right}}). Trade-off matches standard nested-set literature; pattern documented consistently v4.4 through 8.3.
- **来源**:
  - https://www.mongodb.com/docs/v7.0/tutorial/model-tree-structures-with-nested-sets/
  - https://www.mongodb.com/docs/manual/applications/data-models-tree-structures/

## 被否决的断言(Refuted)
- The documented cost of the Subset Pattern is additional database round trips whenever the offloaded data is needed, so the report's optimization plan (splitting text into a separate collection) would make fetch-node-content require an extra query or $lookup — a regression the current benchmark suite does not measure and that could offset gains in subtree-fetch latency.  _[0-3]_  
  来源:https://www.mongodb.com/company/blog/building-with-patterns-the-subset-pattern
- MongoDB's official recommended way to fetch a subtree under the Materialized Paths pattern is a regular-expression query on a comma-delimited path string field (e.g. db.categories.find({ path: /^,Books,/ })), not a lexicographic range scan; a fair MongoDB benchmark of subtree fetch should use this idiom.  _[0-3]_  
  来源:https://www.mongodb.com/docs/manual/tutorial/model-tree-structures-with-materialized-paths/
- An index on the path field makes root-anchored subtree queries significantly faster in MongoDB, which supports the report's proposed fix (indexing the path) for the large-subtree-fetch weakness — provided the query is anchored at the root of the path string.  _[0-3]_  
  来源:https://www.mongodb.com/docs/manual/tutorial/model-tree-structures-with-materialized-paths/

## 未决问题(只能靠实验回答)
- Does a fat covering index (multi-KB summary strings as index keys) actually outperform document fetches for the 36k-row subtree query on MongoDB 7.0 in practice, given index bloat and cache pressure — or does the FETCH-free plan lose its advantage? No empirical data exists in any verified source; this needs a direct experiment before the report claims the fix works.
- How do batched $in multi-gets (chunks of ~500 ids) on MongoDB compare to repeated point reads and to SQL IN-lists — and does the answer change between cache-resident and disk-bound regimes? No surviving claim addressed $in performance characteristics at all.
- Does WiredTiger reclaim on-disk space after delete_tree without an explicit compact, and how do the four engines compare on delete throughput plus space reclamation — a dimension MongoDB staff (familiar with WiredTiger's no-auto-shrink behavior) would likely probe?
- Does the report's pure-read concurrency test suffer from coordinated omission, and would a YCSB-style mixed reader+writer workload with corrected latency recording change the cross-engine concurrency ranking? The DBTest'18 source covers cold/hot separation but the coordinated-omission critique was never verified against the report's harness.

## 注意事项 & 证据缺口
(1) Coverage gap: of the eight dimensions the research question asked to investigate, only cold-cache, $lookup/embedded joins, covered queries, and tree-pattern alternatives produced surviving verified claims. Vector/embedding search and FTS (Atlas Search vs Community options, pgvector), mixed read/write concurrency, multi-tenancy/selectivity, deletes and space reclamation, batched $in performance characteristics, $graphLookup, change streams, multi-document transactions, and coordinated-omission/variance methodology critiques have NO verified findings here — their relevance should be treated as plausible but unsubstantiated by this research pass, and the report should not cite this synthesis for them. (2) Source class: the evidence is overwhelmingly MongoDB vendor documentation — the correct primary source for 'what MongoDB documents/sanctions' claims, but zero independent performance measurements survived; no claim quantifies how much any proposed fix helps. (3) Staleness asymmetry: the $lookup anti-pattern guidance predates MongoDB 6.0's slot-based execution engine, which materially improved eligible $lookup stages; the qualitative guidance still ships in the current manual, but 2019-era magnitude assumptions may overstate the penalty on 7.0. (4) A refuted claim (0-3) asserting that text-splitting makes fetch-node-content regress via extra round trips means the COST side of the Subset Pattern split was not verified — the trade-off exists in the docs' own caveats but its benchmark impact is unquantified. (5) Three near-duplicate materialized-path claims citing the tutorial URL were refuted 0-3 while overview-URL versions passed 3-0, suggesting verifier sensitivity to citation precision rather than substance; cite both URLs in the report. (6) One finding contains a 2-1 split-vote sub-claim (path-index performance wording). (7) All doc pages verified as of 2026-06-12; the 16 MiB limit is stable since MongoDB 1.8 and the index-key-limit removal since 4.2, so time-sensitivity is low, but manual URLs track the latest version (8.3) — pin v7.0 URLs in the report.
